# Design: Server-enforced coordinator completion gate

Generated by office-hours on 2026-08-04

Status: APPROVED

Mode: Builder

## Problem Statement

Clay's task preview can correctly show workers that need attention while the coordinator simultaneously presents an apparently final, successful result. The task graph and the conversation therefore disagree about whether the overall job is finished. Users must interpret colors, open worker sessions, and decide what remains, even though the coordinator owns the delegated work.

Clay already sends every worker result back to the coordinator with instructions to reconcile it, retry or delegate follow-up work, independently verify it, and call `resolve_task`. The screenshot with four attention-needed workers demonstrates that prompt guidance is insufficient as a completion invariant.

The rule must be project-agnostic and provider-agnostic: a coordinator cannot declare the overall job complete until every delegated task has a recorded resolution.

## What Makes This Cool

The worker bar becomes a trustworthy progress metric instead of a diagnostic panel the user must understand. A coordinator's final answer carries a strong promise: every task has been completed, deliberately dismissed, or converted into one precise decision that only the user can make.

During reconciliation, Clay can quietly show `Resolving 4 · 7 done`. It does not add chat noise. The chat interrupts the user only for a genuine decision or the unified final result.

## Premises

1. The coordinator owns worker closure; users should not manually chase workers.
2. Active or attention-needed tasks prevent overall coordination from becoming complete.
3. The coordinator may retry, replace, follow up, independently verify, or dismiss a task with a durable reason.
4. User input is requested only when human judgment is unavoidable, using one precise question.
5. Progress belongs in the worker bar. Chat is reserved for decisions and the final result.
6. Success means all tasks are resolved, not that every task must have the `completed` outcome.
7. These semantics belong to Clay's orchestration protocol, not a repository prompt or project configuration.

## Approaches Considered

### A. Automatic reconciliation nudge

At each coordinator turn boundary, inject another internal follow-up when attention-needed tasks remain.

- Effort: Small
- Risk: Medium
- Benefit: Reuses `pendingCoordinatorUpdates` and existing tools with a small diff.
- Limitation: Still depends on model compliance, has no durable dismissal or user-decision state, and can loop.

### B. Server-enforced completion gate — selected

Give the task graph explicit resolution semantics and derive an overall coordinator phase from server-owned state. Unresolved attention triggers bounded reconciliation. Only a fully resolved graph permits overall completion; a recorded user decision permits a deliberate pause.

- Effort: Medium
- Risk: Low–Medium
- Benefit: Makes the invariant enforceable, observable, persistent, and provider-independent.
- Cost: Touches task lifecycle, tools, turn-boundary handling, persistence, UI, and tests.

### C. Dedicated orchestration supervisor

Move execution and reconciliation into a standalone deterministic supervisor with a richer state machine.

- Effort: Large
- Risk: Medium
- Benefit: Strongest long-term public-product architecture and observability.
- Limitation: More machinery than the current project needs and a larger migration surface.

## Recommended Approach

Implement Approach B as a small server-authoritative protocol layered onto the existing task graph.

### 1. Separate execution status from resolution status

Existing execution statuses remain meaningful: `queued`, `ready`, `running`, `reviewing`, `needs_input`, `blocked`, `failed`, and `completed`.

Overall graph classification becomes:

- Resolved: `completed`, `dismissed`, and legacy `cancelled`.
- Waiting for user: `waiting_user`, only when accompanied by a recorded question.
- Unresolved: every other status, including `failed`, `blocked`, `needs_input`, and `reviewing`.

`failed` can remain terminal for one worker attempt while still being unresolved for the coordinator. This distinction prevents a failed worker from accidentally counting as a finished overall job.

Persist resolution metadata on the task:

- `resolutionReason`
- `resolutionSummary`
- `resolvedAt`
- `userQuestion`

Every transition remains represented in `orchestrationEvents`.

### 2. Add explicit coordinator resolution operations

Keep `resolve_task` for independently verified completion.

Add a dismissal operation requiring a non-empty reason. It transitions the task to `dismissed`, stops or archives its worker, and retains the task and event history instead of removing it from the graph.

Add a user-decision operation accepting one question and one or more affected task IDs. It transitions those tasks to `waiting_user`, persists the question, and permits the coordinator to pause. The next genuine user message reopens those tasks for reconciliation.

The existing close button should use the same durable dismissal semantics with the reason `Dismissed by user`, instead of splicing the task out of the graph.

### 3. Derive a coordinator phase on the server

Derive, rather than manually maintain, one of five phases:

- `executing`: workers are queued, ready, or running.
- `reconciling`: attention-needed tasks remain and coordinator action is possible.
- `waiting_user`: unresolved work is blocked by one recorded user question.
- `stalled`: bounded reconciliation made no graph progress and needs an explicit retry.
- `complete`: every task is resolved.

The phase must survive restarts by being recomputed from persisted tasks. Session-list and active-session payloads should expose it to the web app.

### 4. Enforce the gate at coordinator turn boundaries

Extend the existing `onTurnDone` orchestration hook:

1. Flush worker-result updates as it does today.
2. Classify the coordinator graph.
3. If workers are still executing, allow the coordinator to wait for their existing completion notifications.
4. If attention-needed work remains, enqueue an internal reconciliation turn.
5. If a valid user question is recorded, pause without another automatic turn.
6. If all tasks are resolved, mark the coordination phase complete and allow the unified final state.

The model's provider-level `done` event remains a turn boundary; it no longer implies that overall coordination is complete.

### 5. Bound automatic reconciliation

Store a graph digest and no-progress count for reconciliation turns. Reset the count whenever task state, resolution metadata, or the event sequence advances.

After two consecutive reconciliation turns without graph progress, inject a stricter final reconciliation instruction. After a third no-progress turn, stop automatic continuation and enter `stalled`. Show the unresolved tasks and a `Retry reconciliation` action. Do not manufacture a user question when no human judgment is actually required, and never spin indefinitely.

### 6. Make the web app describe action, not colors

Recommended collapsed labels:

- `3 active · 4 resolving · 7 done`
- `Resolving 4 · 7 done`
- `1 decision needed · 10 resolved`
- `Reconciliation stalled · 4 unresolved`
- `11/11 resolved`

Colors remain secondary status cues. Yellow rows should expose the coordinator's current action or the recorded user question. Dismissed tasks count as resolved, remain auditable in the expanded view, and can be visually muted.

A premature model response can still stream, but the UI must present it as an interim coordinator turn while the server phase is `executing` or `reconciling`. Only the `complete` phase presents the result as the final coordinated outcome.

### 7. Dependency behavior

A dismissed or cancelled dependency is not equivalent to successful completion. Its dependents become blocked until the coordinator replaces the dependency, changes the plan, or dismisses those dependents with reasons. This preserves explicit accountability throughout the graph.

## Open Questions

1. Whether the no-progress limit should be configurable later; the initial fixed default should be three turns.
2. Whether resolved workers should remain in the expanded list indefinitely or collapse into a historical count after the coordination session ends.
3. Whether one user question may cover multiple tasks; the recommended initial behavior allows this when all affected task IDs are recorded.
4. Whether a future public version should automatically try a stronger provider route before entering `stalled`.

None of these questions blocks the initial implementation.

## Success Criteria

1. A coordinator cannot reach overall `complete` while any task is active, failed, blocked, reviewing, or needs input.
2. Worker results that need attention automatically produce a reconciliation turn without user intervention.
3. Completed, dismissed, and waiting-for-user outcomes are persisted and recover correctly after restart.
4. Every dismissal has a reason and remains in the task/event audit trail.
5. Waiting for the user exposes exactly one recorded question and resumes on the next genuine user message.
6. Automatic reconciliation cannot loop beyond the bounded no-progress policy or fabricate a need for human input.
7. The worker bar uses textual phase and counts, so meaning never depends on color alone.
8. Existing provider routing, worker retries, dependency scheduling, and close/archive behavior continue to pass regression tests.
9. The behavior is identical across repositories and model providers without project-specific instructions.

## Dependencies

- `lib/orchestration-task-graph.js` for task and dependency semantics.
- `lib/project-task-orchestrator.js` and a new focused completion-gate module for reconciliation behavior.
- `lib/project-runtime.js` for the existing coordinator turn boundary.
- Orchestration tool schemas and handlers for dismissal and user decisions.
- Session projection/persistence for coordinator phase and resolution metadata.
- `lib/public/modules/orchestration-task-preview.js` and its CSS for action-oriented metrics.

The new completion-gate logic should live in a dedicated module below 500 lines. It should not be added inline to `project.js` message handling.
