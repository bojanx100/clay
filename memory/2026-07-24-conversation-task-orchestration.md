# Design: Conversation-First Task Orchestration

Generated by office-hours on 2026-07-24  
Status: DRAFT  
Mode: Builder

## Problem Statement

Clay currently lets a user add messages while a session is working, but a
single executor processes the resulting work serially. The user must either
wait, manually create and coordinate more sessions, or decide whether a new
message should steer current work or become later work.

The desired experience is one continuous conversation with one coordinating
AI. The user keeps expressing intent; the coordinator decides how to
decompose, order, staff, verify, and report the work across sessions,
sub-agents, providers, and models.

The product goal is to maximize completed useful work per unit of human
attention, elapsed time, and model cost. It should first make Bojan's own work
easier, then let team members contribute through the same coordination model,
and remain understandable and reusable as an open-source project.

## What Makes This Cool

The user no longer manages agents. They talk to one capable coordinator while
Clay quietly forms a task graph and assigns bounded work to disposable
workers. A task board makes the coordinator's interpretation visible and
correctable without turning the user into a project manager.

For example:

> Fix the reconnect issue. Also update the docs, and afterward check whether
> the same bug exists in the Codex adapter.

Clay can represent this as:

```text
Investigate reconnect issue
├── Fix shared reconnect logic
├── Check Claude adapter
├── Check Codex adapter
└── Update docs ── waits for final behavior
```

Independent work runs concurrently. Dependent or conflicting work waits.
Mechanical tasks use cheaper models; difficult reasoning can be promoted
without moving unrelated tasks to an expensive model.

## Product Premises

1. There is one stable coordinating AI per conversation. Users normally
   communicate with it rather than individual workers.
2. Every actionable request becomes part of a shared task graph, even when it
   executes immediately.
3. The coordinator chooses whether a message steers current work, extends a
   task, creates a dependency, or starts parallel work.
4. The coordinator chooses the worker form, provider, model, and verification
   depth within user-defined policy.
5. The task board is an explanation and correction surface, not the primary
   place where work must be administered.
6. Workers are disposable execution contexts. They receive the smallest
   useful brief and return structured progress, results, evidence, or a
   request for input.
7. Promotion and demotion happen per task. The coordinator retains
   conversational and product continuity.
8. Configuration describes policy rather than workflow mechanics: optimize
   for cost/speed/reasoning, maximum concurrency, allowed providers, budgets,
   and approval boundaries.
9. Voice, CTO mode, schedules, team contributions, and text chat submit intent
   into the same task system rather than creating separate orchestration
   products.
10. A coordinator decision must be reversible. The UI briefly exposes
    classifications such as "Steering current task" or "Started parallel
    task" and lets the user correct them.

## Approaches Considered

### A. Smart queue

Keep one executor and classify new messages as steer-current or queue-next.

- **Effort:** Small
- **Risk:** Low
- **Advantages:** Fast to ship; reuses queued-message handling; validates
  intent classification.
- **Disadvantages:** Preserves the elapsed-time bottleneck; provides little
  multi-provider value; risks building a queue abstraction that later needs
  replacement.

### B. Coordinator with session workers

The coordinating AI maintains a task graph and delegates bounded tasks into
existing Clay sessions or sub-agents. A compact board projects task state.

- **Effort:** Large
- **Risk:** Medium
- **Advantages:** Delivers the intended experience while reusing sessions,
  providers, worktrees, handoffs, task launchers, and existing sub-agent UI.
- **Disadvantages:** Requires reliable worker contracts, workspace isolation,
  integration rules, and cross-provider context packaging.

### C. Native orchestration runtime

Build a persistent task-graph engine whose workers acquire execution leases.
Conversation, voice, schedules, teams, and CTO mode all become clients of the
same runtime.

- **Effort:** Extra large
- **Risk:** High
- **Advantages:** Clean long-term scheduler with durable dependencies,
  retries, budgets, auditability, and multiple input surfaces.
- **Disadvantages:** Delays validation; duplicates or absorbs parts of
  sessions, loops, and task launchers; introduces a large subsystem before
  proving the daily interaction.

## Recommended Approach

Build **Approach B**, but define its contracts so ordinary sessions are an
executor adapter rather than the permanent orchestration model. This delivers
the real one-coordinator/many-workers experience using working Clay
primitives, while leaving a controlled migration to Approach C.

This design complements the existing
`docs/roadmaps/planned/CTO-ORCHESTRATOR-ROADMAP.md`:

- Conversation task orchestration handles decomposition and execution inside
  the user's active flow.
- Coop remains the daemon-level conversational coordinator.
- CTO mode adds persistent backlog ownership, autonomous prioritization,
  done-gate enforcement, and reporting.
- The same task records, worker snapshots, routing decisions, and evidence
  should serve all three.

The task board should initially be a projection within the conversation UI,
not a second dashboard the user must visit.

## Approach B Shape

### Coordinator

The coordinator owns intent and task-graph decisions. It:

1. Classifies each incoming utterance or message.
2. Creates or updates tasks and dependencies.
3. Decides which ready tasks can safely run concurrently.
4. Requests worker placement from the scheduler.
5. Monitors structured worker snapshots rather than repeatedly polling full
   transcripts.
6. Integrates results, commissions verification, and reports one coherent
   outcome.
7. Escalates only decisions that need the user.

The coordinator must not do all execution itself. It remains available for
conversation, correction, and product judgment while workers run.

### Scheduler

The scheduler is deterministic where possible. Given a ready task and policy,
it selects:

- execution form: current session, sub-agent, isolated session, or worktree;
- provider and model;
- concurrency slot;
- context and cost budget;
- required verification;
- retry or escalation behavior.

The cheapest capable route is preferred. Failed or unexpectedly difficult
work can move to a stronger route. Provider health and availability affect
placement without changing task identity.

### Workers

Workers receive a versioned task brief containing:

- goal and acceptance criteria;
- relevant project and workspace;
- scoped context and dependencies;
- files or subsystem ownership;
- permission and budget limits;
- required result/evidence contract.

Workers report normalized states:

```text
queued
ready
running
blocked
needs_input
reviewing
completed
failed
cancelled
```

A provider-specific session is only one implementation of this contract.
Workers do not change product intent and do not recursively form unmanaged
teams.

### Task board

The board shows:

- task title and status;
- dependency and parent relationships;
- assigned worker/provider/model;
- concise current activity;
- cost or usage when available;
- blockers and decisions requiring attention;
- verification state.

Primary actions are reprioritize, correct classification, pause, cancel, retry,
and inspect. Creating and wiring every task manually is deliberately not the
normal flow.

### Concurrency and code isolation

Read-only work can run freely within the configured concurrency limit.
Mutating work needs declared scope:

- Non-overlapping tasks may use isolated worktrees concurrently.
- Tasks touching the same subsystem are serialized unless the coordinator
  establishes an explicit integration plan.
- A worker result is not automatically the shared final state. Integration
  and verification are separate task roles.
- Repository rules and human approval constraints remain authoritative.

## Migration Contract: B to C

Approach B must not encode orchestration state only in session metadata. The
following boundaries make conversion to a native runtime possible.

### Stable task identity

Tasks receive orchestration-owned IDs. Session IDs, provider thread IDs, and
worktree paths are executor bindings that may change across retries.

### Executor adapter

Session spawning, sub-agent delegation, and future native workers implement a
shared adapter:

```text
start(taskBrief, placement)
steer(taskId, revision)
pause(taskId)
cancel(taskId)
snapshot(taskId)
collectResult(taskId)
```

The task graph never directly depends on provider session internals.

### Durable event ledger

Coordinator decisions and task transitions are appended as typed events.
Current board state is a projection. This matches the Voice roadmap's durable
conversation ledger and prevents a future migration from scraping chat
transcripts.

### Versioned schemas

Task briefs, snapshots, decisions, verification evidence, and results are
versioned provider-neutral records. Existing `coordinator` message origin and
conversation snapshots should be reused instead of defining parallel formats.

### Policy boundary

Routing receives task characteristics and user policy, then returns a
placement decision with reasons. It must not be scattered across composer,
session, provider, and board code. A native scheduler can later replace this
decision function without changing the coordinator UX.

### Storage boundary

Phase B may persist a lightweight graph beside existing session state, but it
uses its own namespace. Deleting orchestration state cannot corrupt ordinary
sessions, and disabling orchestration leaves delegated sessions usable as
normal Clay sessions. This preserves the CTO roadmap's kill-switch semantics.

## Relationship to Existing Clay Primitives

- `sessions-queued-messages.js` provides current pending-message visibility,
  but queues become one possible task relationship rather than the top-level
  model.
- `project-task-launcher.js` demonstrates spawning tracked sessions from
  external tasks.
- `project-debate.js` demonstrates one agent coordinating multi-provider
  sessions.
- `provider-agent-pipeline.js` supplies an initial delegation contract and
  escalation vocabulary.
- `handoff-package.js` and `handoff-context.js` supply scoped cross-provider
  context transfer.
- `project-provider-failover.js`, `provider-health.js`,
  `model-capability.js`, and `model-recommendations.js` seed placement policy.
- `session-worktree.js` and project worktree creation supply isolation.
- Existing sub-agent rendering supplies initial worker activity UI.
- The Voice roadmap's ledger, typed gateway, input provenance, and executor
  snapshot should become shared substrate.
- The CTO roadmap's routing brain, done gates, and reporting consume the same
  task system at a broader autonomy level.

## Configuration

Avoid a collection of queue/orchestrator/multi-agent modes. Present a small
policy surface:

- **Optimization:** Balanced, Fastest, Lowest cost, Deepest reasoning
- **Maximum parallel tasks:** a numeric ceiling with a conservative default
- **Providers:** allowed routes and optional preferences
- **Budget:** per-task and time-window ceilings when usage data is available
- **Autonomy:** which task classes may start, mutate, commit, push, or ship
  without approval

Advanced users may inspect route explanations and override an individual task.
Defaults must be usable without configuration.

## Open Questions

1. What is the smallest provider-neutral task and snapshot schema that works
   across Claude, Codex, and Copilot?
2. Should the first coordinator be the active session model, a separate
   persistent Coop session, or a cheap deterministic classifier fronting a
   stronger coordinator?
3. Which message classes can be safely identified without a model call?
4. What exact file/subsystem ownership declaration is sufficient to allow
   parallel mutation?
5. Who integrates concurrent work: the coordinator, a dedicated integration
   worker, or the last owning worker?
6. How should cost be normalized when providers expose different usage and
   subscription information?
7. Which task-board details remain visible by default without making the chat
   feel like project-management software?
8. How are team-member intents attributed, authorized, and reconciled when
   they affect the same task graph?

## Success Criteria

The first useful slice succeeds when:

1. While one task is running, the user can add another request and Clay
   correctly exposes whether it steered, depended on, or ran beside the first.
2. Two independent tasks execute concurrently through different workers
   without manual session creation.
3. One dependent task waits and starts automatically after its prerequisite.
4. The user can correct a mistaken classification without reconstructing the
   work.
5. The coordinator remains responsive to status questions while workers run.
6. Worker failure or provider unavailability preserves task identity and can
   retry on another route.
7. Concurrent mutations do not silently overwrite one another.
8. The final response integrates worker outcomes and verification evidence
   rather than dumping several unrelated finals.
9. The same workflow works with at least two provider families.
10. Compared with manually running sessions, the slice reduces elapsed time
    and user coordination actions on several real Clay tasks.

## Next Steps

1. **Observe before coding.** Label 30-50 real queued messages from recent
   Clay usage as steer, elaborate, dependent task, independent task, status,
   correction, or ambiguous. Record where Bojan would disagree with an
   automatic decision.
2. Define the provider-neutral task, task-event, worker-snapshot, and result
   contracts, including stable identity and versioning.
3. Prototype one conversation with two independent read-only workers and one
   dependent worker using ordinary Clay sessions.
4. Add the smallest inline board projection necessary to understand and
   correct those three tasks.
5. Add mutating workers only after worktree ownership and integration rules
   are explicit.
6. Introduce model routing after the task lifecycle works; routing must not
   mask orchestration failures.
7. Feed the resulting contracts into the CTO and Voice roadmaps so those
   initiatives consume, rather than duplicate, the task system.

## What I Noticed

Bojan consistently pushed toward fewer exposed concepts: not separate queue,
multi-worker, voice, and CTO experiences, but a better flow in which "one AI
should coordinate sub tasks." The task board was attractive as a way to keep
track of what is happening, not as another system to administer. Cost and
reasoning quality were named together, which makes task-level model routing a
core requirement rather than a later optimization. The intent is grounded in
daily personal use and already extends naturally to teammates and other users
of the fork.
