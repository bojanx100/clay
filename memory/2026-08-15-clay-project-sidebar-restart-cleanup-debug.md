# Debug report: Clay project sidebar restart cleanup

- **Symptom:** The ordinary Clay project sidebar showed the persistent Coop project coordinator `585c5ab9-8526-498a-8a88-7fc105a290ac` as `Project coordinator` and the legacy restart task `ea632d36-f673-4fb8-953d-892bf010e2d6` as a failed attention row.
- **Root cause:** The server intentionally strips the private `coopControlledBy` reference from session-list broadcasts and exposes only `leadOwned`, but the client suppression predicate required the stripped object. Separately, the legacy task was correctly failed by `restart_recovery`; generic cleanup preserves every failed task and had no typed evidence transition for a later owner-approved restart and verified successor revisions.
- **Fix:** Ordinary project projection now suppresses `leadOwned` project-coordinator roots using the actual broadcast shape. Coop derives each projected root title from its project (`Clay coordinator`, `Webapp coordinator`) instead of trusting stale session metadata. A fail-closed restart supersession reconciler binds the exact failed task/controller to completed revisions 5-8 and commits `c24865ed8a`, `6f4cf56e5e`, `1fa9ed0f6d`, and `cbe920dc4b`. On project registration it changes only that binding and session projection to `superseded`, records the normalized evidence packet, and hides the session without inventing successful completion or deleting its transcript.
- **Evidence:** The live durable records passed a read-only production-rule simulation with one reconciliation and zero blockers. Relevant integration tests passed 165/165. The full repository run passed 2545/2575; the same 30 pre-existing activation-baseline failures remain confined to `coop-control-execution-target`, `coop-control-store`, and `project-task-orchestrator`. Canary recovery events had no new restart entries, and recent loop lag was 3-34 ms.
